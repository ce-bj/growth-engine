# 营销页方案综合分析：流程图、Open Design 与竞品

日期：2026-09-11。本文是分析与建议，不代表已修改产品或完成集成。

## 1. 核心结论

以《AI智能落地页-运营链与访客链.drawio》为产品主线，以 Open Design 本次实测的生成机制为设计引擎参考，以 Instapage / Unbounce 的模块编辑、发布及优化机制为产品化参考。

当前目标是：按意图规划并生成独立营销页，发布为官网真实 URL，通过自然搜索、站内内链、横幅及可选广告承接访客，表单进入询盘系统，效果回到运营端。内链和横幅是分发入口；本轮不需要扩成选型计算器、资料培育或全站改造产品。

建议采用“结构化业务方案 + 可变化的视觉生成 + 平台托管的业务组件”。避免五种类型永远套同一个 HTML，也避免 AI 每次重新编写线索提交和统计逻辑。

## 3. 流程图确定的产品边界

### 运营链

进入生成界面 → 有授权时选择 Ads/GSC 关键词，无授权时由网站档案建议意图 → 确定意图 → 召回企业事实 → 输出页面规划与缺失资料 → 用户确认/修改方案 → 生成内容、视觉与代码 → 质检 → 展示成稿 → 发布服务调用 CMS → 返回站内真实 URL → 询盘与统计回流。

图中明确由产品发布服务对接 CMS，Agent 不直接控制 CMS。该分工适合保留：模型负责方案与设计，业务服务负责站点权限、正式发布和线索处理。

### 调用场景：六类

1. 客户/运营主动做页。
2. SEO 缺少意图承接页，生成页后插入链接；已有页直接复用。
3. 内容运营发文或社媒需要目标 URL。
4. 优化师使用已发布 URL，必要时申请新页；广告账户操作不属于本功能。
5. 其他 Agent 下发出页任务。
6. 定时任务扫描机会并调用同一生成能力。

### 访客路径：四条

- 搜索结果直接进入营销页。
- 从站内内链进入营销页。
- 在相关站内页面通过横幅进入营销页。
- 从广告进入营销页。

六类调用入口、四条访客路径，与页面类型是三个不同维度，不应组合成大量独立模板。

### 需要在文档中明确的阶段冲突

后台泳道写“一期只出数，不自动再生成”；其他图页又包含自动发布、自动调节内链/横幅和自进化。建议明确分期：首期人工确认发布、看数后人工发起修改；后续再引入任务调用、自动发布策略和实验。全景图可以保留，但用阶段标记表达。

“落在错页”建议改称“当前页与目标承接页存在可解释的主题关系”。匿名访客首次进入时，通常不能可靠知道其具体自然搜索词，更不能确定其来错了。首期如实施横幅，应采用当前页面、语言及明确活动参数等可验证条件。

## 4. Open Design 这一次实际如何运行

用户原始需求是：汽车行业的独立营销页，包含公司介绍、汽车介绍，采集保养周期以方便后续推送。

### 已验证的执行链

1. Open Design 创建“汽车服务营销页”项目，将用户需求及通用设计/执行规范交给所选 Coding Agent。
2. 第一轮形成结构化计划：目标用户、交付 HTML、内容模块、表单行为、响应式约束、视觉规范与假设。
3. 宿主接受并固定计划，再续接同一个原生会话执行生产。本次是 simple 模式，没有多 Agent 分工记录。
4. Agent 获取维修场景图片并验证文件类型和尺寸；前两次素材获取不可用，随后得到实际 JPEG。
5. Agent 直接写出 index.html，包含 HTML、CSS、JavaScript；图片保存在 assets/workshop.jpg。
6. Open Design 识别入口文件并展示预览，保存产物信息及文件版本。运行状态记录交付入口有效。

项目的 skill_id 和 design_system_id 均为空，冻结的选定 Skill 包为空。因此不能说此次成稿由某个专用“营销页模板 Skill”生成。它使用了通用设计约束，并在生产阶段加载媒体处理规范。

### 计划中真正起作用的内容

- 视觉：深蓝、中性灰、高对比白色及少量琥珀色；紧凑标题、8px 间距节奏、轻圆角表单。
- 结构：首屏价值、公司介绍、车型服务、服务方式、保养登记。
- 交互：锚点跳转、字段校验、成功反馈、键盘焦点。
- 适配：移动端至桌面端；用 CSS 变量管理颜色、间距等。
- 原型假设：公司和车型使用可替换示例；登记成功为页面内模拟反馈。

Open Design 的可借鉴之处是“先确定设计决策，再按决策写出可编辑页面”。本次没有选定设计系统，不等于没有设计规范。

### 为什么这张页面比本地原型更贴近需求

- 标题围绕“保养提醒”这个用户收益展开。
- 表单字段为称呼、手机号、车型、上次保养时间、预计周期，匹配这次任务。
- 使用维修场景实图，配合有主次的按钮和分区布局。
- 公司介绍、车型服务和服务步骤均服务于保养登记。
- 布局能根据内容和屏幕变化，没有强行沿用工业产品询价页面。

这是基于本次成稿和代码的判断，不代表所有 Open Design 输出都具有相同质量，也不能证明上线转化率。

### 这张成稿的业务边界

HTML 的提交事件只有 preventDefault、输入校验、显示成功状态和禁用按钮，没有调用后台保存接口。因此姓名、手机号、保养周期没有由这段代码写入业务系统，也没有建立推送任务。

“一车一档、提前提醒、记录可查”目前是页面展示内容；没有相应业务实现证据。图片来自外部网站，本次没有验证商业使用授权，正式企业页应替换成已确认的企业素材或有明确使用权的素材。

原型里“按行驶里程提醒”也没有采集当前里程和提醒阈值，说明视觉与前端交互完整不等于业务字段充分。

本次运行事件可证明素材检查和交付验证；没有发现浏览器视觉复检及自动修复循环的调用，不能将其描述成已经完成全面视觉 QA。

### 如何打开与运行

在 Open Design 中打开“汽车服务营销页”的 index.html 即可预览。产物是静态 HTML，没有 React/Vite 构建要求；保留 index.html 与 assets 目录的相对位置即可用浏览器打开，或部署为静态页面。正式上线仍需要门户发布接口、表单接口和事件统计。

## 5. 与本地 marketing-agent-app 的关键区别

| 环节 | 当前本地原型 | Open Design 本次成稿 | 建议 |
|---|---|---|---|
| 业务入口 | 选意图→预制方案→工作室 | 一句话需求→内部计划 | 保留现有运营入口 |
| 文案 | generate_copy_draft 填固定文本；存在工业电源默认值 | 按汽车保养任务撰写 | 改为基于确认事实的结构化文案生成 |
| 页面结构 | 五种类型最终共用 _HTML_TEMPLATE | 为此次任务生成布局和样式 | 让方案真实决定模块与视觉 |
| 局部修改 | 已有 data-region 选择和对话修改入口 | 桌面提供预览、代码、版本等能力 | 复用现有入口，限制修改范围 |
| 表单 | 仅改变按钮文案 | 有字段校验，但仍只显示成功 | 统一接平台表单服务 |
| 正式发布 | HTML 预览，未接 CMS | 本地产物预览 | 用独立发布服务接现有 CMS |
| 企业事实 | 向导与后端 Mock 不一致 | 未提供企业资料，使用占位 | 统一企业事实与素材来源 |

特别注意：当前 render_page 接收 page_type，但没有用它选择不同页面结构；它也没有接收完整的区块文案列表。仅改善提示词，不能保证确认的展会信息、FAQ 等进入最终 HTML。必须改生成输入与输出协议。

## 6. Instapage 与 Unbounce 的设计阶段如何借鉴

### Instapage：模块生产、编辑与复用

官方支持预设/自建 Instablocks、保存复用、拖拽编辑、协作及页面发布。建议借鉴稳定的模块身份、可替换布局、可复用企业证据模块，而不是首期重建完整自由画布。

### Unbounce：设计与转化动作一起配置

官方支持页面元素编辑、表单、确认状态、变体、弹窗/浮条和优化能力。建议每个 CTA 除文案外，同时配置动作、目标、表单及成功/失败状态；页面变体绑定版本和统计口径。

动态文案替换主要参考已知活动参数及广告匹配场景，不推导为能够读取当前自然搜索访客的具体查询。

### 推荐分工

| 来源 | 借鉴内容 | 不直接照搬 |
|---|---|---|
| 你的流程图 | 意图、事实、确认、CMS、分发、询盘、效果闭环 | 一期就自动进化的全景范围 |
| Open Design | 结构化设计方案、任务适配出稿、可编辑产物 | 原型成功反馈作为正式业务成功 |
| Instapage | 模块管理、替换、复用、协作 | 首期重型自由拖拽编辑器 |
| Unbounce | CTA/表单配置、预览、版本和转化统计 | 小流量下无依据的自动胜出 |

## 7. 建议的目标流程

选意图/接受任务 → 查已有承接页 → 生成预制方案 → 核对企业事实与缺口 → 确认区块文案 → 生成视觉成稿 → 局部调整与质检 → 绑定正式表单与统计 → CMS 发布 → 返回 URL → 分发与看数。

沿用已有五种业务类型：产品营销、留资获客、品牌实力、促销活动、展会邀请。采购阶段用于调整表达、证据和 CTA，不再另造三套类型。设计风格独立于业务类型，例如同一产品营销页可选择技术参数导向或场景图片导向。

### 在“预制方案”中增加的设计信息

- 页面目标：用户要完成什么，企业希望收集什么。
- 模块顺序：每一块回答哪个问题。
- 事实与素材：内容从哪里来，缺什么，缺失时隐藏还是阻止发布。
- 视觉方向：企业色、首屏布局、图片风格、信息密度；默认推荐一套，允许切换。
- 转化定义：主 CTA、必要字段、数据去向、成功反馈。

初稿后支持点选模块并用自然语言修改。已确认事实与主转化动作默认锁定；只换颜色无需重审文案，若新增承诺则将相关内容重新标记待确认。

## 8. 可落地的生成机制

建议保存一份结构化 PageSpec，包含 intent_id、page_type、事实引用、模块 ID、确认文案、素材 ID、视觉参数、表单 ID 和 CTA 动作。

让模型根据 PageSpec 生成差异化视觉区块；表单提交、客户身份、统计、发布由平台组件和服务统一实现。首期可采用“生成 HTML 区块＋稳定区域 ID＋托管业务插槽”，但必须验证与门户 CMS 的页面模型是否兼容。自由 HTML 不会自动变成可拖拽模块。

最少存三类成果：结构化方案、可编辑设计源码、正式发布快照。修改生成新版本；发布的是已审核版本，不是模型当前正在改写的文件。

质检分三层：事实是否可靠；页面与交互是否可用；线索是否真实入库。先验证可用性，再用真实数据验证转化效果。

## 9. 建议实施顺序与验收

### 第一步：证明设计引擎确实改善成稿

保留向导和文案确认，统一事实输入，替换固定文案填充及单一 HTML 出稿。用同一企业的产品页、留资页、品牌页做比较；有真实活动资料时再覆盖促销与展会。

验收：页面结构符合类型；已确认文案完整进入页面；没有串入另一企业的数据；关键交互可用；能局部修改；移动端可读；记录耗时和人工修改次数。Open Design 的汽车页作为视觉与交互参考，不作为 B2B 转化基准。

### 第二步：完成一个真实闭环

对接现有表单和 CMS，形成一个站内真实 URL，并从一处现有内容建立入口。测试实际提交、失败、重复提交、询盘入库，以及 page_id / intent_id / version_id / UTM 的传递。只有后端返回保存成功才显示提交成功。

### 第三步：再扩大分发与优化

接 GSC/Ads 候选、复用页面查询、批量任务；之后再做横幅、实验与自动化。不要把所有能力塞进首期出稿工作室。
